Content Pattern Library

A rules-based content system for admin dashboards, case views, status panels, forms, and notifications. Shifts content work from bespoke authoring to reusable patterns — so IXD can design at pace and CD governs with leverage.

Design principles

P-01  Rules before words
Encode logic; write once, reuse many.
P-02  Smallest understandable unit
Short, front-loaded, scannable.
P-03  Predictable semantics
Same condition, same message shape, every time.
P-04  Escalate exceptions
If a case breaks rules, escalate to CD. Recurring exceptions become new rules.
P-05  Evidence through usage
Retire patterns no one uses; promote those that reduce rework.

Message Anatomy

All content patterns share a common structure. Use these building blocks to compose any message in the service.

{Type}  +  {Subject}  +  {Cause / State}  +  {Effect} (optional)  +  {Action}

Type
status / error / info / success / warning / help
Subject
application / account / task / document
Cause
What happened or what is missing
Effect
What this means (skip if obvious)
Action
Imperative, 1 step only

Status  CPL-01

Summarise state at a glance. Used in rows, cards, and headers. State label set is closed — do not invent new labels per team or product.

Status pattern status:in_review
In review We'll email you if we need more information.
Action needed Upload your ID document by 12 March 2026.
Approved You'll see your payment in 3 to 5 working days.
Rejected Read the reasons and how to appeal.
Draft — 
{{state_label}} — {{explainer}}

Structure

[State label] + optional explainer (≤ 12 words) + optional date/time

Required

  • state_label (from controlled vocabulary)

Optional

  • explainer
  • timestamp

When to use

  • Table rows and lists
  • Card headers
  • Page headers
  • Inline summaries

✓ Do

  • Use the closed set of state labels
  • Keep explainers ≤ 12 words
  • Use the same explainer for the same condition across the service

✕ Don't

  • Invent new labels per product or team
  • Use colour alone to signal state
  • Embed a second action in the explainer
  • AC-1Status uses approved label from controlled vocabulary (Draft, In review, Action needed, Approved, Rejected, On hold, Expired, Completed, Scheduled, Paused).
  • AC-2If explainer is present, it is ≤ 12 words with no second action embedded.
  • AC-3Status chip always includes text — never colour alone. Programmatically associated with the entity via aria-label or heading context.

Warning  CPL-02

Prevent harm or costly mistakes. Three-part structure: Cause → Impact → Required action.

Warning banner warning:payment_mismatch
! Warning There's a mismatch in your bank details. You will not be paid.
Update your account details
! Warning You're close to the deadline. Your application may be delayed.
Submit it today 
There's {{cause}}. {{impact}}. {{action}}.

✓ Do

  • Put impact in plain terms (what will happen to the user)
  • Make the action a button wherever possible
  • Keep cause specific and factual

✕ Don't

  • Blame the user
  • Bury the action after long explanations
  • Use for low-risk informational messages
  • AC-1Warning uses three-part structure: cause → impact → action.
  • AC-2Primary action is focusable and immediately follows the impact statement.
  • AC-3Region announced to screen readers (role="alert" on dynamic insertion; govuk-warning-text component for static).

Error  CPL-03

Explain what went wrong and how to fix it. Page-level summary + field-level messages.

Error summary + field error error:invalid_format

There is a problem

  • National Insurance number — Enter a number in the correct format, like QQ123456C
  • Date of birth — Enter a valid date of birth
It's on your National Insurance card, payslip or P60.

Error: Enter a National Insurance number in the correct format, like QQ123456C. 

// Field-level — required
Enter your {{field}}.

// Field-level — invalid format
Enter a {{field}} in the correct format, like {{example}}.

// Field-level — mismatch
Your {{field}} doesn't match {{related_field}}. Check and try again.

// Page-level heading (always)
There is a problem

✓ Do

  • Point to the exact field to fix
  • Give one fix per message
  • Provide a format example when relevant
  • Place page summary above the first field

✕ Don't

  • Use technical codes or database messages
  • Hide the page summary above the fold
  • Say "invalid" without explaining how to fix
  • AC-1Error summary appears above the form with heading "There is a problem" using the govuk-error-summary component.
  • AC-2Each list item anchors directly to its field (href="#field-id").
  • AC-3Field error text linked via aria-describedby. Error text is visually adjacent to the field.

Form Label + Help  CPL-04

Ask for information unambiguously. Prefer a question to a noun label. Use hint text for how/where.

Label, hint and example form:label_hint
You can find this on your payslip. For example, 12345678.
It's on your National Insurance card or P60. For example, QQ123456C.
Label: {{question}}
Hint: {{how_or_where}}. For example, {{example_value}}.

✓ Do

  • Use user language, not internal field names
  • Prefer a question to a noun label
  • Keep hints to ≤ 14 words

✕ Don't

  • Stack multiple instructions inside labels
  • Rely on placeholders as labels
  • Put essential info only in tooltips
  • AC-1Each input has a visible label element programmatically associated via for/id.
  • AC-2If hint text is present, the input references it in aria-describedby.
  • AC-3Examples appear as part of hint text — not as placeholder-only content.

Conditional Question  CPL-05

Ask follow-up questions only when relevant. Reveal child fields immediately when the condition is met.

Interactive conditional demo form:conditional

Do you have a UK bank account?
It's 6 digits, for example 01-23-45.
It's 8 digits, for example 12345678.
Parent: {{question}}
Child (shown when {{condition}}): {{follow_up_question}}

✓ Do

  • Reveal child content immediately when condition is met
  • Keep child questions close to the parent
  • Move focus to first revealed field where appropriate

✕ Don't

  • Reveal multiple unrelated groups at once
  • Break tab order when showing or hiding content
  • AC-1Conditional content only renders when the user selects the triggering option.
  • AC-2Uses govuk-radios--conditional pattern with data-aria-controls. Focus management handled by govuk-frontend JS.
  • AC-3Tab order remains logical when content is shown or hidden.

✓ Do

  • One concept per cell
  • Show relative + absolute dates where timing matters

  • Wrap whole paragraph sentences in cells

  • AC-2Status cells use govuk-tag with text. Never colour alone.
  • AC-3Column order matches the agreed content model. Abbreviations from controlled vocabulary only.

{{what_happens_next}}

✓ Do

  • Put the result in the title (past tense: "Application submitted")
  • Offer a clear next step above the fold
  • Specify timeframes concretely

  • Repeat the entire form contents
  • Show "success" for events the user didn't initiate

Guidance Block  CPL-08

Short, actionable guidance within a flow. 2–3 bullets max. Use when users repeatedly ask the same question.

Inset guidance guidance:inline

Proving your identity

  • Use a photo of your passport or driving licence.
  • Make sure all four edges are visible.
  • The image must be clear and not blurred.
How to take a clear photo 
{{heading}}
- {{action_or_rule_1}}
- {{action_or_rule_2}}
- {{action_or_rule_3}}  [optional]

Learn more: {{link_text}}

✓ Do

  • Keep bullets parallel (same grammatical form)
  • Prefer 2–3 bullets max
  • Use meaningful link text

✕ Don't

  • Repeat content already visible on the page
  • Use for essential task-critical information
  • AC-1Uses govuk-inset-text component with a govuk-heading-s and govuk-list--bullet.
  • AC-2Links use descriptive text. No "click here" or "read more" without context.

Multi-step Instructions  CPL-09

Help users complete complex tasks reliably. One action per step, starting with a verb.

Numbered steps instructions:multi_step

To verify your bank details, follow these steps:

  1. Download the verification file.
  2. Upload it to your bank portal.
  3. Return to this page and select Confirm.

Keep this tab open while you complete the steps.

Download verification file 
To {{outcome}}, follow these steps:

1) {{step_1}}
2) {{step_2}}
3) {{step_3}}

Tip: {{tip}}

✓ Do

  • Start each step with a verb
  • Keep each step to one action
  • List prerequisites upfront

✕ Don't

  • Use nested lists where possible
  • Write steps longer than one sentence
  • AC-1Steps render as govuk-list--number (<ol>). Each step is one sentence or action maximum.
  • AC-2Primary CTA appears after the list, not before it.

Tooltip / Definition  CPL-10

Explain domain terms without cluttering the UI. Short definition (≤ 14 words) + one example. Must be keyboard-accessible.

Term tooltip tooltip:definition

Your gross pay Your pay before tax or deductions. For example, £2,000. is used to calculate your contribution rate.

Enter your UTR number Your 10-digit Unique Taxpayer Reference from HMRC. For example, 1234567890. to continue.

Hover over the i buttons or the underlined terms to see definitions.

{{term}} — {{short_definition}}. For example, {{example}}.

✓ Do

  • Keep definition ≤ 14 words
  • Use the controlled vocabulary
  • Make tooltips focusable for keyboard users

✕ Don't

  • Use for essential task-critical information
  • Rely on hover only
  • AC-1Tooltip trigger is focusable (tabindex="0") and available to keyboard and touch — not hover-only. abbr element also exposes definition to AT.
  • AC-2Tooltip text mirrors the controlled vocabulary glossary entry exactly.

System / Meta Message  CPL-11

Communicate background processes, scheduled events, or deprecations. Always clarify whether the user needs to act.

System message system:background_event

Important

Your documents are being scanned. You can continue using the service.

Scheduled update

We'll update your dashboard overnight. You'll see new data from 6am tomorrow.

{{event}}. {{effect}}. {{user_action_if_any}}

✓ Do

  • Be precise about timing (6am, Monday, overnight)
  • Clarify whether the user needs to act

✕ Don't

  • Show "success" for events the user didn't initiate
  • Use vague timing like "soon" or "shortly"
  • AC-1Uses govuk-notification-banner component. Dynamic insertions use role="alert" for urgency or role="status" for polite updates.
  • AC-2All timeframes are explicit. No "soon", "shortly", or "later".

Decision Trees

Keep these in your repo or Confluence. IXD uses them as parameters for UI copy; CD updates rules — not every screen.

Status decision tree

IF required_documents_missing = true THEN status = "Action needed" explainer = "Upload the missing documents." ELSE IF review_started = true AND decision_ready = false THEN status = "In review" explainer = "We'll email you if we need more information." ELSE IF decision = "approved" THEN status = "Approved" explainer = "You'll see your payment in 3 to 5 days." ELSE IF decision = "rejected" THEN status = "Rejected" explainer = "Read the reasons and how to appeal."

Error decision tree

IF field_empty THEN msg = "Enter your {{field}}." ELSE IF invalid_format THEN msg = "Enter a {{field}} in the correct format, like {{example}}." ELSE IF rule_conflict THEN msg = "Your {{field}} doesn't match {{related_field}}. Check and try again." // Warning decision tree IF payment_details_mismatch THEN warn = "There's a mismatch in your bank details. You will not be paid. Update your account details." IF approaching_deadline THEN warn = "Deadline is {{date}}. Submit now to avoid delays."
